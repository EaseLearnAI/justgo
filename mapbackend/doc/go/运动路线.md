# 一、先把“热量”这个概念拆干净（非常关键）

你现在实际上有 **3 种不同性质的热量**，但目前混在了一起：

## 1️⃣ 摄入热量（Input）

* 来自拍照识别
* 本质是：**估算值**
* 用途：记录 & 提示

## 2️⃣ 累积未消耗热量（Backlog）

* 比如你说的：

  > 前两天没运动，欠下来的热量
* 本质是：**长期健康指标**
* ❌ **绝对不能直接用于一次运动决策**

## 3️⃣ 本次建议消耗热量（Target）

* 真正要用于：

  * 路线长度
  * 运动时间
  * 强度
* 必须是：
  **受控、有限、可完成**

👉 **你现在卡住的地方就在于：把 2️⃣ 当成了 3️⃣**

## 一、先给你一个“总原则”（非常重要）

## 二、不要让用户选「上限」，而是选「感受区间」

### 选项示例（非常关键）

用户只是在选「感觉」，而不是数值。

## 三、你内部怎么把“感受”转成真正的运动上限？

这是你关心的技术层，我给你一套**非常稳妥的映射逻辑**。

### 1️⃣ 建立一个「用户基础能力指数」（系统算，不让用户算）

基于你已经有的：

* 性别
* 年龄
* 体重
* 身高
* 最近运动记录（哪怕很少）

你可以维护一个 **Movement Capacity Score（MCS）**（不用暴露给用户）。

例如：

* 新手 / 久坐：0.6
* 普通人：1.0
* 经常运动：1.3

---

### 2️⃣ 把“感受 × 目标 × 能力”合成「单次安全区间」

#### 举个非常清晰的例子：

用户：

* 目标：减脂
* 感受选择：🙂 微微累
* 能力系数：0.7（新手）

系统内部得出：

```json
{
  "max_duration_min": 20,
  "max_calorie_burn": 180,
  "intensity": "low-moderate"
}
```

而另一个用户：

* 目标：减脂
* 感受：🙂 微微累
* 能力系数：1.2

可能是：

```json
{
  "max_duration_min": 35,
  "max_calorie_burn": 300
}
```

👉 **用户选的是同一句话，但你给的是完全不同的“安全上限”**

这才是真正的个性化。

## 四、把「减脂 / 维持 / 增肌」变成“策略权重”，不是命令

这是第二个关键点。

### ❌ 不要这样理解目标

* 减脂 = 每次都要多消耗
* 增肌 = 每次都要强度拉满

这会直接把人搞崩。

---

### ✅ 正确理解：目标 = 长期策略权重

你可以这样用：

| 目标 | 单次运动策略           |
| -- | ---------------- |
| 减脂 | **频率优先，强度保守**    |
| 维持 | 稳定输出，波动小         |
| 增肌 | 强度可波动，但**次数不能少** |

📌 关键一句话：

> **目标影响“节奏”，不影响“安全边界”**

---

## 五、你真正要做的，不是“一次到位”，而是“爬坡”

这是你这个项目最有价值的一点。

### 建议你一定要引入一个概念：

> **推荐 ≠ 固定
> 推荐 = 可增长**

### 设计一个「自适应上限」

#### 逻辑非常简单，但极其有效：

* 连续 3 次完成推荐 → 上限 +5~10%
* 中途多次放弃 → 自动下调
* 用户完全无感知

📌 用户感受到的是：

> “怎么感觉最近走得越来越远了，但也没那么累？”

这就是你要的 **坚持感**。
